# Phase 5.5 — Reference Palette Lock Design (+ Oklab palette snap)

**Date:** 2026-07-25
**Status:** Draft (awaiting review)
**Related:** [PLAN.md](../../../PLAN.md) Phase 5.5; addresses AI animation frame color drift

## Background

AI image models produce animation frames whose colors **drift slightly** between frames — the same nominal "red" comes out as `(220,40,40)` in frame 1 and `(215,45,38)` in frame 2. For coherent pixel-art animation the frames must share **one** palette.

The current pipeline does **not** solve this automatically:
- k-means (`seed=42`) is deterministic per image, but centroids are derived from **each frame's own pixels** → different inputs produce different centroids → drift persists. Deterministic ≠ cross-frame consistent.
- The only existing lever is `--palette <hex>` / `--preset` (lock output to a fixed palette), but the user must supply the palette by hand.

Phase 5.5 adds **reference-frame palette lock**: derive a palette from one reference frame (via the existing Oklab k-means) and snap every target frame to it. Plus a small consistency fix: `apply_palette` currently snaps in RGB distance while `quantize` clusters in Oklab — unify on Oklab.

## Scope — two parts

### A. `--palette-from <ref.png>` (reference palette lock)

Derive a palette from a reference image and use it as the fixed palette for the target.

- **`palette.rs::extract_palette(bytes, k_colors, colorspace) -> Result<Vec<[u8;3]>>`** — load ref → run existing Oklab k-means (with `dither = None`, `preset = None` so the output is clean k-color, no dither intermediates) → collect unique RGB from the quantized output (skipping transparent pixels) → return as `Vec<[u8;3]>`. ~15 lines, pure reuse of `quantize::quantize`.
- **Config**: add `palette_from_path: Option<String>` (CLI-only, mirrors existing `input_path`/`output_path` — `#[allow(dead_code)]` under wasm).
- **CLI**: `--palette-from <ref.png>` sets `palette_from_path`. The CLI run path (single + batch) loads the ref **once**, calls `extract_palette`, and sets `config.palette`. In batch mode the same derived palette applies to every frame → cross-frame consistency.
- **Precedence**: `--palette <hex>` (explicit) > `--palette-from` (derived) > `--preset`. If both `--palette` and `--palette-from` are given, `--palette` wins (extraction skipped). Documented.
- **WASM**: new export `extract_palette(bytes, k_colors) -> String` returning comma-separated hex (`"0d2b45,ff6b6b,..."`). The JS caller calls it on the reference, then passes the result as the existing `palette_hex` param to `process_image`. No new bytes-param on `process_image` — clean split, reuses the palette path.
- **Determinism (R1)**: ref k-means uses `config.seed` (42) → same ref → same extracted palette → same target output. Byte-reproducible.

### C. Oklab palette snap (consistency fix)

`nearest_palette_color` ([palette.rs:45](../../../src/palette.rs)) currently uses RGB squared-Euclidean; switch to **Oklab squared-Euclidean** (reuse `quantize::oklab::rgb_to_oklab`), matching `quantize`'s distance space.

- **Cost**: trivial — `apply_palette` already caches per unique input color (`HashMap<[u8;3],[u8;3]>`), so the sRGB→Oklab conversion runs once per unique color, not per pixel.
- **Anchor impact**: default config has `palette = None` → `apply_palette` doesn't run → Oklab anchor `3a589ee9…e4420` and RGB anchor `802857…9f22` **unchanged**. Only `--palette` users see a (more accurate) difference. No version bump (optional path, default unaffected).

## Non-Goals

- **Batch `--lock-palette-to-first`** convenience (first input file auto-used as ref) — thin wrapper on top of A; defer until users ask.
- **Shared batch k-means** (pool all frames' pixels, one global k-means) — mathematically optimal but bigger engineering; A is the 80/20.
- **Palette-from with dither/preset on the ref** — extraction deliberately runs clean k-means only (dither would inflate the unique count past `k_colors`).
- **New UI** — Web palette editor is Phase 6 (U4.6); this is the core algorithm.

## Determinism, testing, anchors

- **R1**: `extract_palette` is deterministic (seeded k-means + deterministic unique-collection order — sort the palette for stable ordering, since `HashSet` iteration is nondeterministic). Test: extract twice from same ref → byte-identical hex.
- **Cross-frame consistency test**: synthesize frame1 (red `220,40,40`) + frame2 (red `215,45,38`) → extract palette from frame1 → apply to both via `--palette-from`/`palette_hex` → assert both frames' reds snap to the **same** palette entry.
- **Oklab snap test**: a pixel equidistant in RGB but not Oklab snaps to the perceptually nearer entry.
- **Anchor lock**: default-config Oklab/RGB anchors unchanged (A doesn't touch default path; C only runs under `--palette`).
- **Re-lock**: any existing test using `--palette` gets a new anchor under C (Oklab distance changes nearest mapping).

## Acceptance

- Same reference image → `extract_palette` returns byte-identical hex across runs (R1).
- Two AI-drift frames locked via `--palette-from` end up using the same palette colors (drift eliminated within snapping tolerance).
- `apply_palette` uses Oklab distance (consistent with `quantize`); cache keeps it cheap.
- Default-config anchors unchanged; `cargo test` green; wasm 0 warnings.

## Risks

| Risk | Mitigation |
|------|------------|
| Option C changes `--palette` output → existing palette tests break | re-lock affected test anchors; default path untouched |
| `extract_palette` unique-collection order nondeterministic (HashSet) | sort palette before returning (stable hex output) |
| batch ref file missing/unreadable | explicit error, no silent fallback to per-frame k-means |
| ref palette size < `k_colors` (empty clusters) | return whatever uniques exist; `apply_palette` handles any non-empty palette |
